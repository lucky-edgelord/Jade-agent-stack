Playbooks

Portable YAML automation over Vault, Base, Kit and local commands; check, plan, run, approve.

A playbook (*.playbook.yaml) compiles to each target's existing primitives: Base tools, Vault's HTTP API, a Kit page and local commands. It does not replace Vault playbooks, flows or Jade Lisp. The schema is schema/playbook.v1.json (and jade docs show playbook-schema).

Example

apiVersion: jade/v1
kind: Playbook
metadata: {name: base-products, description: A products collection}
spec:
  targets: [base]
  scopes: [read, write, schema]        # the run's short-lived task credential
  vars: {collection: products}
  defaults: {fail_mode: rollback}
  tasks:
    - name: Products collection
      tool: collection_create
      args: {name: "{{ collection }}", fields: [{name: title, type: text}]}
      register: col
      undo: {tool: collection_delete, args: {name: "{{ collection }}", confirm: "{{ collection }}"}}

Targets

TargetToolsNotes
baseevery tool the token may use (jade base tools)arguments are checked against the tool's schema at check time
vaultchat, flow, status, flows, chats, historyVault-only tools (ui_render, notify) run inside a Vault flow
kitpagewrites a page that runs Kit in a browser
localcommand: "…"allowed by approvals.shell

A task without target goes to the one allowed target that owns the tool; two owners is an error.

Expressions

{{ name }}, {{ created.result.id }}, {{ items.0 }}, literals, == != < <= > >= and or not in, filters default(x) lower upper trim json length string int. {% raw %}…{% endraw %} keeps text as it is. No calls, no imports, no I/O. An unknown name is an error unless | default() is used.

Failure modes

ModeOn a failed task
stopstop the run (default)
continuego on with the next task; the run stays ok (use it for checks like "is it there?")
rollbackrun each finished task's undo in reverse, then stop. check refuses a rollback playbook whose mutating tasks lack undo

Idempotency and resume

Every mutating call carries a key: sha256(playbook | task | vars) by default (idempotent_strategy: key), content-hash (the rendered arguments) or none (a new UUIDv7 each run). Base runs a key once and replays the first answer. Runs are recorded in ~/.local/state/jade/runs/; running again with the same vars resumes, skipping finished tasks. States: not_started, in_progress, completed, refused, failed, interrupted, resumable.

Approval

A playbook that changes Vault or Base starts unapproved. jade playbook approve NAME signs its SHA-256 with a local key; any edit invalidates it. Unattended runs (--no-input, MCP, HTTP) need the approval; interactive runs ask.

Schedules

spec.schedule: "every weekday at 9am" needs the vault target: jade playbook plan prints the equivalent Vault schedule. Base has no scheduler, by design.

Commands

jade playbook list | check | plan | run | approve | revoke | logs NAME [--var k=v …] [--json]
